## 容器内存误判与 OOM

最初依据主机 `free` 显示的约 503 GiB 内存设置 FlashAttention 的 8 路编译，遗漏了容器的实际限制。这是本次搭建的资源判断错误。容器 `memory.max` 只有 68,719,476,736 bytes，即 64 GiB；`cpu.max` 为 `800000 100000`，等效 8 个 CPU 核；`/dev/shm` 只有 4 GiB。

高并发编译触发了 cgroup OOM，观测到 8110、8112、8114 三个已有推理服务退出。记录当时累计计数为 `oom=19`、`oom_kill=12`；这些是容器计数，不能解释为三个服务各自重启了多少次。基线评测产生的 173 条连接错误被重新排队，已成功的预测保留。

修复包括把编译并发降到 2，按实际 cgroup 限制设置训练资源，并记录 `current_bytes` 与扣除 `inactive_file` 后的 `working_set_bytes`。根编排器每 5 秒采样；工作集超过限制的 94% 时，仅向本次实验子进程组发送 SIGTERM 并标记失败。文件缓存可以被内核回收，不能只凭 `memory.current` 触及 64 GiB 就声称发生了新的 OOM。

8110 和 8112 已按原配置恢复并通过模型接口健康检查；8111 未改动。旧 9B 服务的进程身份、命令与必要环境变量已保存，训练使用其释放的 GPU 3–6，计划在三教师训练与评测全部完成后逐个恢复。

证据：`runtime/memory_incident.json`、`evaluation/restored_4B0.json`、`evaluation/restored_4B2.json`、`runtime/previous_9b_servers.json`、`runtime/released_9b_servers.json`。成功完成的旧单步检查期间 OOM 计数没有继续增加。

## 训练和推理环境不能直接混用

原有 `pre-lab/venv` 用于既有推理服务，版本与训练仓库不一致。训练另建 `.venv-train`，没有覆盖原环境。训练固定 torch 2.10.0、transformers 5.5.0、vLLM 0.18.0、Ray 2.53.0、FLA 0.4.2，完整依赖位于 `logs/training-environment.freeze.txt`。

vLLM 0.18.0 的包元数据要求 transformers 小于 5，而当前训练 fork 使用 5.5.0。因此 `pip check` 的这一条冲突被明确记录，其他冲突不被忽略。包能够导入不代表训练可用，实际四卡单步更新与导出才提供运行证据。`dependency-metadata.json` 的安装阶段标志本身不代表后续 GPU 验收状态。

另一个依赖约束来自 OpenCV 4.13 对 NumPy 2 的要求。本环境采用 NumPy 2.2.6，同时满足 vLLM 所用 numba 的上界；没有继续照搬 fork 中不兼容的 NumPy 1.26.4。

证据：`logs/dependency-metadata.json`、`logs/import_preflight.log`、`training/setup_train_env.sh`。重建时应使用留存的版本和脚本，避免无记录地升级某个核心包。

## FlashAttention 没有可直接使用的匹配 wheel

torch 2.10 和 Python 3.10 的组合未取得匹配的 FlashAttention 预编译 wheel，转为从固定的 2.8.3 源码构建。完整通用构建开销较大，最终按本模型需要编译 BF16、head dimension 64 和 256 的内核，保留前向、反向、causal、noncausal、varlen 与 split-KV 路径。

关闭的功能是 dropout、ALiBi、softcap、非整齐 head dimension 和 local attention。Python 与 C++ 接口均显式拒绝未编译的调用；不能将这个 wheel 当作任意模型都能使用的通用发行包。CUDA 架构使用 sm80 目标并在本机 L20 上验证。

GPU 数值检查覆盖所需前向与反向，并与 SDPA 结果比较。源码 tarball、补丁、构建配置和 wheel 都已保留。wheel SHA256 为 `0c53be067de6fd4e5a38efd07f388b4cfd3c58cc1ced790c2da677394cc0ec9f`。

证据：`logs/flash-attention-build.json`、`logs/flash-attention-source.patch`、`logs/flash-attention-validation.json`、`build_sources/wheels/`。

## 四个进程先在 CPU 加载完整模型会超过内存预算

Qwen3.5-4B 的实际模型参数约 4.54B，包含共享的 embedding 与输出权重。四个 rank 各自在 CPU 生成完整 FP32 权重副本，再分片，会消耗过多的容器内存；参数和优化器再做 CPU offload 也不适合当前 64 GiB 限制。

为本实验增加了显式可选的 `load_tied_weights_on_gpu` 路径：先在对应 GPU 流式加载共享权重，再执行 FSDP2 分片。参数、优化器和 policy 的 CPU offload 均关闭。主参数与梯度归约为 FP32，前向使用 BF16；所有教师采用相同设置。

单卡加载探针和四 rank 实际初始化均通过。单卡 FP32 探针约占 16.91 GiB GPU；这是初始化探针，不能用来估计包含梯度、优化器和激活的训练峰值。

代码位于 `pre-lab/repo/verl/workers/fsdp_workers.py` 与 `verl/workers/config/engine.py`；证据为 `logs/gpu-load-probe.json` 及各 run 的 `repository.patch`。

## 模型分片列表类型不兼容导致首轮检查失败

第一次真实四卡检查在 FSDP 初始化阶段遇到 `TypeError: 'set' object is not subscriptable`。当前模型的 `_no_split_modules` 是集合，而 fork 中的代码按可下标列表处理。

在 `pre-lab/repo/verl/utils/fsdp_utils.py` 中，仅对 `set` 和 `frozenset` 做排序并转为列表，再进入既有逻辑。这次失败发生在任何参数更新之前。修复后的检查通过了模型加载、分片和优化器初始化。

失败日志保留在 `runs/perception_smoke_failed_20261019_233252/`；不要将该目录当作可恢复的训练 checkpoint。

## 多序列拼接实测发现跨样本干扰

审查该 fork 的 Qwen3.5 前向补丁时，发现线性注意力路径没有消费打包序列所需的 `cu_seqlens` 边界。随后按用户要求完成真实四卡测试：调用实际 `DataParallelPPOActor._forward_micro_batch`，使用两条真实图文样本、四轴 mRoPE、相同响应 token 和损失分母，比较独立、原生 packed、padded 与进程内分段 linear 控制，并做重复、换序、双向因果干预和全模型梯度比较。

原生 packed 模式中，固定后条的图片、token、位置与 mask，仅改变前条的非 EOS 响应顺序，后条 log-prob 最大变化 AB=0.902136、BA=0.751673；同输入重复与 padded 对照均为 0。进程内分段 linear 后，观测到的跨样本前向干扰和换序差归零。这里已有实际因果控制证据，不再只是静态风险推断。

但分段模式对独立计算的梯度相对 L2 差仍有 0.3804/0.3768，其自身重复噪声约 0.0156/0.0181；padded B2 也未通过梯度等价检查。残差可能涉及批形状、BF16 或底层 kernel，但本次尚未分离原因，不把某一猜测写成定论。FSDP2 能执行 B2，不等于当前 Qwen3.5 混合注意力的跨样本拼接语义正确，也不能反过来说 FSDP 天生不支持 packing。

当前采用每 GPU microbatch 一条序列，关闭 actor 和 old-logprob 的 dynamic batching。单条序列内部仍可去掉 padding，前向使用 `use_cache=False`，FLA 初始状态为空；通过梯度累积保持当前正式全局 batch 30 个 prompt、每组 8 条回答；packing 决策时的 batch 40 后经用户批准降低。

这是实测后的正式选择，保持用户要求的 batch 与 group。短样本探针虽有约 1.5–1.9 倍局部前向提速，但不构成正确性通过，也不能外推完整 RL step。该测试未覆盖 8192 长响应、优化器状态或完整 PPO 更新；原生动态分组还按有效 token 近似计费而保留全局 padding，不能直接启用 padded dynamic。后续优化须先解释并解决梯度差，再做长序列完整训练检查。

证据：`logs/packing_probe/结果说明.md`、`report.json`、`inputs.json`、`response_log_probs.pt`、`run_01.log`；执行决定为 `runtime/packing_decision.json`。探针独立后台运行并正常退出，没有修改生产代码或权重。

## 旧概率复用和熵开关需要落实到执行路径

仓库原入口包含 Vision-OPD 蒸馏配置，本阶段实际需要独立的教师 GRPO。训练入口改为 vanilla clipped GRPO，没有使用蒸馏 loss。

此外，单纯把 entropy coefficient 设为零不保证代码不计算熵；复用 vLLM rollout log-prob 也不能验证训练与生成后端的概率差异。因此实际执行路径明确关闭熵计算，关闭 KL loss 和 KL reward，并由 HF actor 重新计算 old log-prob。生成与训练之间使用上限为 2 的 token importance correction。

日志中的 approximate KL 或 `rollout_corr/kl` 是诊断值，不是损失中的 KL 正则。旧成功单步中 old-logprob 重算耗时 119.2 秒，IS 均值约 1.000327；日志里的 IS min/max 包含截断前统计，不能据最大值超过 2 就断言 cap 没生效。

证据：`pre-lab/repo/verl/trainer/ppo/ray_trainer.py`、`verl/workers/fsdp_workers.py`、旧成功 run 的 `training.log` 和 `smoke_execution_validation.json`。

## 多图 prompt 的 2048 上限需要按视觉 token 计算

仅截断文本字符或普通 tokenizer 长度不能保证 VLM prompt 符合 2048 token。ViRL 含多图问题，图片展开后的 token 和 chat template 都必须计入预算。

当前输入配置每图像素上限为 `min(786432, 1572864 // 图片数)`，最小像素 4096，最多 8 图。agent loop 使用实际 processor 计算长度，只截断普通用户文本的中部，保留头尾、视觉标记和回答格式要求。若图片与模板本身就无法放入预算，显式失败，不能截断图片 token 序列。

真实 CPU processor 检查覆盖 3、4 和 8 图情形。评测使用相同的输入像素预算配置，但两套实现不能据此认定逐图处理完全相同；评测超长题采取统一排除，不采用每模型不同的临时裁剪。10 月 20 日的全 header 审计进一步确认训练有两次 resize，第二次 HF processor 默认最小面积为 **65,536**，会再次放大小图，故配置的 4096 不是最终下限。审计调用实际安装的两份纯 resize 函数，仅读 20,061 个不同图像 header，不解码全库或使用 GPU。最终单图视觉 token 为 `H_final*W_final/1024`，一份 FP32 图像载荷字节为 `sum(H_final*W_final)*24`；乘 group 8 后，batch 30 的感知/推理/通用最大单份载荷分别约 **1.369/1.519/1.921 GiB**。这是载荷估计，不是 RSS、副本数或显存可承受证明；数据和图像传输代码保持不变。证据为 `logs/visual_batch30_budget_audit.json`。

## 奖励实现中的真实误判与修复

奖励直接影响 GRPO 的组内优势，不能仅验证“代码运行不报错”。训练前及单步检查中修复了以下问题。

| 问题 | 修复后的规则 | 验证要点 |
| --- | --- | --- |
| ViRL 的金标本身含 boxed，直接比较会误判 | 只对可信金标解开 boxed，模型回答仍须通过最终答案门控 | 9,480 条 ViRL 参考答案通过 |
| 角度符号和数学外层定界符不一致 | 统一度数写法，处理完整外层数学定界符 | 分数、小数、角度与美元定界符例子通过 |
| 数学校验器只抽取 LaTeX 的前一段 | 不允许利用换行命令或多段锚点获得部分答案奖励 | `2\\3` 对金标 `2` 判错 |
| 后一个 boxed 不完整却退回前一个答案 | 最后一个未闭合 boxed 使最终答案无效 | 未完成修正答案判零 |
| VQA 去重会丢失人工标注共识 | 保留 10 位标注员答案的重复次数，计算 leave-one-out 共识 | 3 个相同答案得 0.9，而不是 1 |
| JSON 格式本身可能获得奖励 | JSON 必须是唯一指定字符串字段，随后仍按内容评分 | 额外字段、重复 key、NaN、数字 value 判零 |
| exact 归一化可能丢失负号或运算符 | 数值与文本等价分开处理，保留关键符号 | `-2` 不等于 `2`，`1+2` 不等于 `1-2` |
| 单变量多根表达误判 | 对完整的同变量赋值根列表比较所有根，允许无标签根列表 | `x_1=-3,x_2=2` 与 `-3,2` 相等；漏根、多根、错误变量不等 |
| 普通逗号答案被 math-verify 当作集合 | 普通列表逐项比较，保留顺序和重复次数；千分位按数值处理 | `8,5` 不等于 `5,8`，`-3,-3,-4` 不等于 `-3,-4,-3` |

多根问题在真实 rollout 中被发现：MMK12 的正确回答 8 条全部被旧版本判为 0。完整单步仍产生了其他两组有效优势，所以“梯度非零”不能证明每种奖励都正确。随后数据审查又确认正式样本存在要求按顺序返回多个数值的题目，补上了列表的顺序约束。

旧奖励源码保留为 `logs/rewards_ef9eaba3.py`。最终奖励 SHA256 为 `049236623c27a9b1584ec74a6c8fd81f95914fb949936d8b326804d7f96679b2`，13 项单元测试通过，19,581 条参考答案通过。旧 32 条 rollout 重评分只有 8 条 MMK 答案从 0 变为 1，其余不变。参考答案自一致通过不代表覆盖了所有等价表达，因此反例和实际输出检查仍是必要的。

证据：`tests/test_rewards.py`、`logs/reward_reference_audit.json`、`logs/reward_multiroot_correction.json`。多变量和复杂结构采用保守的完整匹配，可能拒绝某些语义等价但重排的写法；本实现不是通用数学判题器。

## rollout 副本随机种子需要区分

四个 vLLM 副本最初使用相同 seed。旧单步中四组完整回答的不同输出数为 8、8、6、8；DocVQA 有三条完整思考和答案完全相同。重复本身不足以证明随机流复制，但共享 seed 不利于独立采样。

最终仅对 rollout 引擎采用 `base_seed + replica_rank`，四个值分别为 20261019、20261020、20261021、20261022。actor 与模型初始化 seed 保持 20261019，温度、top-p、group 和样本预算不变。CPU 检查执行实际参数赋值，并把映射写入 protocol。

随机生成允许自然重复，检查不设置任意的“至少多少不同答案”门槛。完整输出数量用于审计，组内奖励差异和有效梯度用于验证可学习信号。

## 共享文件系统锁在进程退出后仍阻塞

OOM 后观察到原进程已退出，但 EPC 共享文件系统上的 `flock` 仍阻塞续跑，现象与遗留租约一致；没有取得文件系统服务端诊断。训练、评测和根编排器改用 `/tmp` 下的本机锁，锁名包含工作目录绝对路径的哈希，恢复后流程继续推进，并维持对本机 GPU 和服务的互斥。

恢复流程不会删除已完成的 checkpoint 或成功预测。正式运行若失败，重新启动 driver 会检查数据、代码、配置和环境哈希，并从最近保存的 checkpoint 恢复；未保存的步骤需要重跑。已完成的 300-step 模型和评测缓存会复用。

证据：`run_experiment.py`、`training/launch.py`、评测三个入口的锁实现。不同服务器的本机锁互不协调，不应在另一台机器上同时操作这组本地 GPU 服务。

## 区分真实故障与非阻断警告

实际日志中出现过 CPU Ray server 进程提示找不到 CUDA runtime、较短 dummy sequence 小于 head 数、`VLLM_USE_V1` 未识别、以及缺少 causal-conv1d 的警告。排查分别确认了 GPU worker 的 CUDA 路径、FLA 的真实张量布局，以及 kernel=4 的短卷积回退。没有为清除所有警告而继续安装可选包。

此 fork 的 rollout 通过 Ray engine 调用生成，宣告的 HTTP 端口不提供常规监听；不能用这些端口的 `/metrics` 连接失败判断生成服务已经死亡。训练阶段的进程、GPU 使用、实际 rollout 文件及更新结果是更直接的证据。
