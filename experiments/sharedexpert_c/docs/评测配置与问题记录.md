### 去污染与已完成的审计

每条评测样本保存原图文件 SHA256、RGB 像素哈希和问题哈希。像素哈希的定义为：

```text
SHA256(struct.pack('>II', width, height) + image.convert('RGB').tobytes())
```

问题哈希在 NFKC、casefold、合并连续空白后计算。哈希包括图像尺寸，不能与只对 RGB 字节计算的另一套哈希混用。

## 4. 答案抽取、严格评分与截断

所有题的 prompt 请求将最终答案置于 `<answer>...</answer>`。评分器兼容以下抽取顺序：最后一段完整 `<answer>`；最后一个括号配平的 `\boxed{...}`；最后一行明确答案，去除 `Answer:` 等前缀。它不只接受 XML 标签，因此 **格式抽取成功率不是严格标签合规率**。

### thinking 与回答边界

如果返回中有 `</think>`，只评最后一次闭合后的正文；未闭合 thinking 不得凭其内部出现的正确数字或选项得分。某些 vLLM parser 会把 `reasoning_content` / `reasoning` 与 final content 分开，这种情况下只评 final content。如果没有分离 reasoning，且正文没有 `</think>`，现行评分按未结束思考处理。空回答、选项歧义、无法解析答案都判错，并保留抽取失败标记。

### 各任务的判定

| 任务 | 当前判定规则 |
|---|---|
| 选择题 | 接受单一 A–J 字母、明确以该字母开头的选项表达，或与唯一完整选项文本匹配的答案；不从解释中搜索任意正确字母 |
| Yes/No | 以独立单词 yes 或 no 开头，忽略大小写；`Nothing` 不能被当成 `No` |
| 其他短答案/数值 | 先规范化少量 Unicode、空白和 LaTeX 包装，再精确文本匹配；可解析的整数、小数、科学计数法、简单分数按数值比较 |
| 数值容差 | `abs(pred-gold) <= max(1e-8, 1e-8*abs(gold))`；不是 ChartQA 的 5% 容差，也不是训练 reward 的全部规则 |
| RefCOCO | 必须可解析成 4 个非 bool 数字的 JSON 数组 `[x1,y1,x2,y2]`，坐标在 0–1000，且 `x1<x2, y1<y2`；IoU≥0.5 才算正确 |

数学评分没有调用外部 judge 或完整符号等价证明器。符号等价、单位表达、近似四舍五入和同义答案可能被保守判错，因此结果名称是**本地严格抽取/匹配准确率**，不能直接替代官方 LLM-judge 成绩。对 `exact` 任务，`parse_success` 仅表示抽取到了非空文本，不等于通过数学表达式有效性验证；这也限制了“抽取失败率”可解释的范围。

### `finish_reason=length` 一律记零

即使模型在 8192 token 截断前写出了完整且正确的答案，只要本次终止原因是 `length`，`correct=False`；RefCOCO 的计分 IoU 也置 0。原始答案、解析成功标志、`correct_before_length_penalty` 和必要的 `iou_before_length_penalty` 保留用于审计。`length` 是已完成推理的一种有效失败，不会作为 API 错误反复生成直到答对。

评分协议与生成协议分开版本化。`summarize.py` 每次从原始回答重新计算评分，写入独立 `predictions.scored.jsonl` 和 `scoring.json`，不覆盖正在追加的 `predictions.jsonl`。历史缓存中内嵌的旧 `correct` 字段不应越过当前 scorer 直接用来作表；单纯评分更新无需 GPU 重推理。

API 错误与模型失败也分开：前者保留 `error` 并重试，存在任何未修复 API 错误时整模型不报告最终分数；后者按正确率分母正常计入。

## 5. 三维汇总、置信区间与互补性

实现见 [summarize.py](../evaluation/summarize.py)。各基准先得到 0–1 区间的分数，再在同一维度等权平均：

```text
推理 = (MathVista + MathVision + MMMU) / 3
感知 = (MME_perception + RefCOCO) / 2
通用 = (MMStar + MMBench_circular) / 2
```

### Bootstrap 的实际范围

当前实现固定种子 `20261019`，对每个基准做 **2000 次有放回重采样**，取 2.5% 和 97.5% 分位数作为 95% 区间。相对 baseline 的差值在同一批抽样索引上计算，得到基准级配对差值区间。

分组必须按真实 `group` 字段理解：MME、RefCOCO 按图像像素哈希；MMBench 按循环题组；MathVista、MathVision、MMMU、MMStar 按题 ID。MME 的 240 行落在 110 个图像组，不能假设恰好 120 对。MMStar 的 500 行有 488 个不同图像哈希、MathVista 的 500 行有 494 个，因此后两者的实现并没有将所有共享图像的题合为同一个 bootstrap 簇。

现有代码只输出**基准级** bootstrap 区间和相对 baseline 的配对差值；三维宏平均当前只有点估计，没有三维级置信区间、跨训练 seed 的不确定性估计或多重检验校正。不能把单次训练的题目重采样区间解释为对训练随机性的完整统计证明，也不能仅凭几个区间宣称方法普遍更优。

### 互补性统计及 C 方案边界

## 7. 已遇到的问题、处理与证据

### 7.1 旧 baseline 的预算和 judge 与本次不同

旧项目历史结果使用过 32768 response token、不同采样设置和 DeepSeek judge。本次采用 8192、temperature=0 和本地严格评分。如果沿用旧分数，教师增益会与预算/评分器变化混杂。因此基线重新生成，旧成绩不进入新主表。证据见 [README.md](../evaluation/README.md)、现行 `run.json` 与 `summarize.py` 的报告声明。不能用新旧数字直接证明 RL 提升或退化。

### 7.2 初版图像预算与训练不一致

最早短暂运行使用每图 262144 像素上限，后来统一到 786432。输入视觉分辨率改变会影响 token 数和答案，因此旧生成未直接混入当前结果，原始清单、smoke/core 记录和报告已整体归档到 [old_protocol/image262144](../evaluation/old_protocol/image262144)。当前 README 尾部仍保留该历史阶段的“v2”说明；现行版本应以 suite.meta 的 **v3** 为准。

### 7.3 增加总图像预算后，只有一题需要改变输入

为与训练保持一致，v3 规定每图 `min(786432,1572864//图数)`。审计了 3423 行：3403 行单图、9 行双图、3 行三图、4 行四图、4 行五图。只有 `MMMU_DEV_VAL:10719` 的五张 636×496 图像改变视觉网格，每张图由 320 降为 285 个视觉 token，总 prompt 从 1720 变为 1545；其他 3422 行的有效图像网格及整行 hash 保持一致。

迁移没有重置所有结果：329 条成功生成逐行验证后保留，173 条连接错误不当作成功结果导入。唯一输入变化的题若已有缓存必须失效重推；当时该题尚不在 329 条成功缓存中。原始 502 条记录、旧 suite/meta 和迁移统计保留在 [migration.json](../evaluation/old_protocol/migration_v2_to_v3_total_image_budget/migration.json)。计算审计见 [multimage_budget_audit.json](../evaluation/multimage_budget_audit.json)。

服务端还做了该五图样本的计数诊断，实测 prompt=1545，与冻结值一致，记录在 [v3_image_budget_server_check.json](../evaluation/v3_image_budget_server_check.json)。这次诊断 `max_tokens=1`，**不进入正式回答缓存或任何成绩**，不能写成一次正常 8192-token 评测。

### 7.4 单图服务拒绝 MMMU 多图请求

初次 smoke 使用只允许 1 张图的现有服务，多图请求被拒绝。随后改用原本配置 `image:8` 的 8112；8110/8111 继续保持原单图配置。v2 共 8 题、跨 6 个基准的 smoke 最终完成，含多图示例，API 错误归零；两条 8192-token 截断按现行规则记错。该 smoke 是小样本链路检查，不代表完整基准成绩，也不替代 v3 全量推理。

### 7.5 cgroup OOM 导致服务消失和 173 条连接错误

宿主可见内存很大，但容器实际 `memory.max=68719476736`，即 **64 GiB**；CPU quota 为 8 核。事件记录将 FlashAttention 构建并发 8 引发的内存压力认定为主要原因，记录了 8110、8112、8114 服务丢失。`memory.events` 中 `oom_kill=12` 是当时系统累计计数，不能据此把每一次历史 kill 都归因于本次事件。

构建并发随后降为 2；与训练相关的内存配置调整、资源检查由训练流程处理。评测这边先保存全部缓存，再按原参数和非秘密运行环境顺序恢复 GPU 2/8112 与 GPU 0/8110；GPU 1/8111 的原服务未改动。两者于 2026-10-19 23:16（上海）完成 `/v1/models` 健康验证。证据：[memory_incident.json](../runtime/memory_incident.json)、[restored_4B0.json](../evaluation/restored_4B0.json)、[restored_4B2.json](../evaluation/restored_4B2.json) 和对应 `.log`。

迁移前 core 的 502 个不同 ID 中，329 个成功、173 个连接失败。失败没有被删除后假装评测完成，也没有作为模型答错混入最终准确率；它们在新 finalizer 中重新排队。这 173 个 ID 后续均获得成功响应；在修复当时仍需等待其余题完成，不能仅据“173 错误修复”推断全量完成。最终 baseline 的独立完整性验收于 06:37 确认 3423 行齐全、API 错误为 0。

### 7.6 OOM 后旧 EPC 文件锁阻塞续跑

旧 core/final 进程已不存在，但新 finalizer 在共享 EPC 文件系统的 `.baseline-final.lock` 上等待，进程处于 `epc_pr`。观察与 OOM 后遗留的分布式 flock 租约阻塞一致；未取得文件系统服务端诊断，不能声称已从服务端完全证明其内部原因。

处理时仅停止本次新建、尚未进入推理的等待进程；随后将 finalizer、推理输出目录、教师 GPU 的互斥锁统一放到 `/tmp/sharedexpert-evaluation-locks-<uid>/`，按资源绝对路径和用途哈希命名。本机推理与 GPU 仍互斥，同时绕开旧共享文件锁。恢复后的日志实际出现 `Imported 329 unchanged predictions` 和 `3423 samples, 3094 pending`，之后持续增长，见 [baseline_final.log](../evaluation/baseline_final.log) 与 `common.py:local_lock_path`。

该锁是本机锁，不提供跨不同主机、共享同一输出目录的分布式互斥；当前部署是单机多 GPU，复现时不能在另一台主机同时写同一结果目录。

### 7.7 缓存评分可能沿用旧截断判定

先前已生成的回答可能在截断前包含正确 final，旧缓存内嵌的 `correct` 字段不足以执行现行“length 一律零分”。解决方式是保留原始生成，独立版本化评分，导入、续跑和汇总时统一从 raw 回答重算，保留惩罚前得分便于核查。相关测试覆盖“正确 final + length 仍为零”和“旧缓存正确 bbox 在 length 下重算为零”；见 [test_evaluation.py](../evaluation/test_evaluation.py)。

### 7.8 重复调用和中断清理
